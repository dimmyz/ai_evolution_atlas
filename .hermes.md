# Hermes project rules — AI Evolution Atlas

## 1. Canon hierarchy

1. `spec/ai-atlas/` — product, research, data and acceptance canon.
2. `docs/adr/` — accepted architectural decisions.
3. validated content in `data/` — publishable factual dataset.
4. card body + handoff artifact — official working context for that card.
5. chat, profile memory, `SOUL.md`, critique comments — non-canonical unless merged into canon.

A worker may not silently weaken canon to obtain a green result.

## 2. Global SOUL rule

Global role souls describe **role, temperament and protocol only**.

They must not contain:
- project names;
- repository paths;
- project test commands;
- product-specific acceptance criteria;
- current sprint instructions.

Project context belongs here, in `spec/`, ADRs and card bodies.

## 3. Workspace integrity — mandatory

Every card must contain:
- `project_id: ai-evolution-atlas`;
- expected workspace path;
- expected Git root/repository identity;
- canon paths to read.

Before doing work, every worker must prove the workspace:

1. report current working directory;
2. run `git rev-parse --show-toplevel` if Git exists;
3. confirm `.hermes.md` contains `AI Evolution Atlas`;
4. record current commit/hash in handoff when practical.

Reviewer rejects evidence from the wrong repository even if tests are green.

## 4. Hermes scheduling reality

Hermes parent links may behave as **scheduling gates**, not Jira-style epics.
Therefore:
- keep a logical Sprint ID in docs/titles;
- use dependency edges only for real execution prerequisites;
- do not attach all work cards to an unfinished scheduling parent if that would deadlock them;
- Strateg records actual `t_*` IDs in `docs/reports/sprint-01-card-ids.json`.

## 5. One card, one assignee

One execution card has one accountable assignee.
Parallel cards must have explicit file/module ownership or be serialized.

## 6. Same-card review

For implementation, architecture and research deliverables:

`worker -> required local gates -> request_review -> Reviewer`

Reviewer:
- approve -> card may close;
- request_changes -> same card returns to same worker;
- blocked/escalated -> Orchestrator handles route.

Do not create a redundant “review this card” child task.

A **Critic checkpoint** is different: it is a first-class adversarial analysis artifact, not an acceptance gate.

## 7. Reviewer independence

Default independent Reviewer for significant cards: **Claude Sonnet 5** in a separate profile/session from the worker.

Use Sonnet 5 as an adversarial Critic at designated UX/content checkpoints.
Claude Opus 5 is escalation-only unless the human explicitly changes policy.

## 8. Rework budget

- cycle 1: normal corrections;
- cycle 2: Orchestrator diagnoses why convergence is weak;
- cycle 3: automatic ping-pong stops; escalate to Strateg/human or stronger reviewer.

## 9. Quality is multi-dimensional

Green tests are necessary but insufficient.
The product has five gates:

1. **Factual** — claims and lineage are source-grounded.
2. **Engineering** — tests/typecheck/build/runtime are green.
3. **UX/Visual** — screenshots satisfy the visual contract.
4. **Accessibility/Interaction** — keyboard/basic a11y and browser flows work.
5. **Factory** — correct routing, workspace, handoff and review evidence exist.

## 10. Browser harness from day one

Playwright Chromium must be installed/configured during scaffold, not after a failure.
Agents use the project browser harness; they must not invoke `chrome:` or Store protocol links.
On Windows, prefer `npm.cmd` when PowerShell execution policy blocks `npm.ps1`.

## 11. Shared-file discipline

Parallel feature cards may not all rewrite composition-root files.
Feature cards own isolated directories; one later integration card owns shared composition/root wiring.
If worktree support is available, Strateg/Orchestrator may use it. Otherwise serialize cards that touch the same shared files.

## 12. Human responsibilities

Human approval is expected for:
- material scope changes;
- credentials/privileged actions;
- production publishing;
- final visual/product acceptance.

The human should not be asked to run routine tests.
